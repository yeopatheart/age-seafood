# 2026-09-27 촬영·검수 통합, 스와이프 검수, AI 수량 제안, 성능 개선

`2026-09-25-terminal-dispatch-scope.md`에서 정한 4단계(배정·촬영·송장입력·체크리스트) 구조를 실사용 피드백을 받아 여러 차례 다시 고쳤다. 이 문서는 그 이후 확정된 것들을 정리한다.

## 결정 1: 주문 리스트(orders) 기능 완전 제거
- 배경: 사용자가 "이 앱에서 우선 주문 내역은 불필요합니다"라고 명시. 실제 흐름은 라벨 사진·버스 송장 사진 대조만으로 충분하고, 주문 데이터 없이도 동작해야 함
- 선택: `/orders` 라우트, `orders` 테이블, 관련 체크리스트·배정 UI를 코드·DB 모두 삭제
- 이유: 안 쓰는 기능을 남겨두면 유지보수 부담만 커짐. 나중에 필요해지면 그때 다시 만든다

## 결정 2: 버스 송장 텍스트 입력 폐지 → 사진 + (이후) AI 제안 수량
- 선택: 버스회사명·차량번호·수량을 타이핑하는 폼을 없애고 사진만 찍는다. 이후 결정 5에서 수량만 AI 제안 방식으로 부활
- 이유: 수기 입력은 카톡으로 사진 보내는 것과 실질적으로 다르지 않다는 지적 (아래 "왜 이게 카톡보다 나은가" 참고)

## 결정 3: 촬영 화면과 검수 화면을 하나로 합침 (`/capture`+`/review` → `/deliveries`)
- 배경: 담당자(촬영)와 관리자(검수)가 다른 사람이어도, 탭을 나누는 것 자체가 불필요한 전환 비용이라는 피드백
- 선택: 배송 하나의 상세 화면에서 라벨 사진 촬영, 버스 송장 사진 촬영, 검수를 모두 처리. 하단 내비게이션은 배송/기록 2개로 축소
- 이유: 소규모 팀이라 역할 구분이 화면 구조로 강제될 필요가 없음

## 결정 4: 검수 결과를 "정상/문제있음" 2단계 → 스와이프 하나(검수완료)로 단순화
- 선택: 정상/문제있음 버튼 대신 끝까지 밀면 검수완료 처리되는 스와이프 컨트롤 하나만 둔다. 문제가 있으면 상태값이 아니라 메모에 적는다
- 이유: 사용자가 상태 구분 자체를 없애길 원함. `trip_reviews.status` 컬럼 삭제(마이그레이션 0007)

## 결정 5: 버스 송장 박스 수량 — AI(Claude API) 제안 + 사람 확인
- 배경: "카톡으로 사진 보내는 것과 뭐가 다르냐"는 핵심 질문에 대한 답. 라벨 사진 장수는 이미 자동으로 세어지므로, 버스 송장에 적힌 수량만 자동으로 읽으면 그 자리에서 즉시 일치/불일치를 알 수 있다
- 우려: 사용자가 처음에 수기 입력을 없앤 이유(색연필 손글씨 인식률)와 같은 우려가 버스 송장에도 있음 ("사람들이 글씨를 흘려쓴다")
- 선택: 전통 OCR이 아니라 Claude API(비전)로 이미지를 문맥적으로 읽게 하고, 그 값을 **제안값으로만** 쓴다 — 화면에 "AI가 읽은 값: N"으로 미리 채워두고, 사람이 확인(그대로 저장) 또는 수정 후 저장한다. 절대 자동으로 신뢰하고 넘어가지 않는다
- 이유: 완전자동화가 실패했을 때의 리스크(잘못된 값이 조용히 저장됨)를 없애면서도, "0부터 세기"를 "맞는지 확인만 하기"로 바꿔 체감 노동을 크게 줄인다
- 미검증 사항: 실제 손글씨 인식률은 실사용해봐야 안다 — 정확도가 낮으면 이 기능의 가치가 줄어들 수 있음. `bus_trips.invoice_box_count`(마이그레이션 0008)에 저장

## 결정 6: 라벨 사진 촬영 — 앱 내 카메라 강제 → 갤러리 다중 선택
- 배경: "박스를 트럭에 상차하기 직전에 라벨 촬영을 모두 마친다"는 실제 작업 순서 — 이 시점엔 이미 폰 기본 카메라로 빠르게 찍는 게 최선이고, 앱을 열어 한 장씩 찍게 하면 카톡 방식과 다를 게 없다
- 선택: 라벨 사진은 `capture` 속성을 빼고 갤러리에서 여러 장을 한 번에 불러오게 한다. 버스 송장 사진은 터미널에서 실시간으로 찍는 한 장이라 카메라를 그대로 강제한다
- 이유: 앱이 "지금 당장 찍어야 하는" 시간 압박 지점에 끼어들지 않는 것 자체가 효율화

## 결정 7: 성능 — `getUser()` → `getClaims()`, 사진 업로드·서명 URL 배치 처리
- 배경: "앱 반응 속도가 필수 요소"라는 명시적 요구
- `proxy.ts`·`NavBar`·서버 액션 전부에서 `auth.getUser()`(매번 Auth 서버 네트워크 왕복) 대신 `auth.getClaims()`(JWKS 로컬 캐시 검증)로 교체 — 로컬 측정 기준 요청당 ~350ms → ~7ms. 실제 데이터 접근은 RLS가 매 쿼리 재검증하므로 보안은 약화되지 않음
- 사진 여러 장을 올릴 때 파일마다 서버 액션을 부르지 않고, 병렬 업로드 후 한 번의 insert + 한 번의 revalidate로 처리 (이전엔 파일마다 페이지 전체가 재계산되며 이미 올린 사진들의 서명 URL까지 매번 다시 발급받고 있었음)
- 사진마다 `createSignedUrl`을 따로 부르지 않고 `createSignedUrls`로 한 번에 배치 발급
- 업로드 전 브라우저에서 캔버스로 리사이즈·압축(최대 1600px, JPEG 0.75) — 휴대폰 원본이 수 MB라 약한 네트워크에서 가장 큰 체감 지연 요인
